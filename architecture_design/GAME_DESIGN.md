# Game Design — 산성비 (Acid Rain Typing Battle)

과제(ft_transcendence subject v20.0) 기준으로 "실시간으로 여러 유저가 동시에 상호작용하는 웹 게임"이면
`Gaming and user experience`(Major) · `Remote players`(Major) 요건을 충족한다.

## 1. 게임 개요

- **인원**: 2~4인 배틀로얄(`#91`/`#92`). 기존 1:1(host/guest) 고정 모델을 참가자 배열(`players[]`,
  2~4명)로 확장 — 상세 계약은 `WEBSOCKET_PROTOCOL.md` §0.1/§6.3 참고.
- **핵심 루프**: 서버가 단어를 생성해 참가자 전원에게 **동일한 단어 스트림**을 동시에 브로드캐스트한다.
  화면 위에서 단어가 떨어지고, 먼저 정확히 입력한 플레이어가 그 단어를 지우며 상대방에게 데미지를 준다.
  아무도 지우지 못한 단어가 바닥에 닿으면 산성비를 맞은 것처럼 **생존자 전원**이 데미지를 입는다.
- **승패**: **마지막 생존자 승리**(last-survivor-wins). HP가 0 이하가 된 참가자는 즉시 탈락하며, 남은
  인원이 2명 이상이어도 매치는 계속된다. 매치 종료 시점(180초)까지 2명 이상 생존해 있으면 HP가 가장
  높은 참가자가 승리(동률이면 공동 우승/무승부)한다. 상세 규칙은 §3.1 참고.
- **서버 권위**: 단어 스폰 시각/순서, 정오답 판정, 데미지 계산, 탈락/순위 판정은 전부 서버가 결정한다.
  클라이언트는 서버가 보낸 이벤트를 그리기만 하며, 클라이언트 로컬 타이머로 판정하지 않는다(레이턴시
  조작 방지).

## 2. State Machine

```
WAITING → COUNTDOWN → IN_PROGRESS → FINISHED
```

| Phase | 설명 | 트리거 |
|---|---|---|
| `WAITING` | 로비에서 두 플레이어가 방에 입장, `SET_READY`로 준비 완료 대기 | 로비 프로토콜(`WEBSOCKET_PROTOCOL.md` §0)에서 처리, `/game` 네임스페이스 진입 전 |
| `COUNTDOWN` | `match_ready` → `match_start`(동기화된 시작 시각) 사이의 짧은 카운트다운 | 양쪽 소켓이 `join_room` 완료 |
| `IN_PROGRESS` | 단어 스폰 루프 동작, HP 변동, 재접속 처리 | `match_start` 이후 |
| `FINISHED` | HP 0 도달 / 180초 경과 / 상대 퇴장(FORFEIT) | `match_end` 브로드캐스트, `MatchHistory` 저장 |

## 3. 핵심 메커닉 (MVP 확정 수치)

### 3.1 HP & 매치 종료 (2~4인 배틀로얄, `#92`)
- 참가자 전원 HP 초기값 `100`.
- **탈락**: 특정 참가자의 `HP <= 0`이 되는 순간 **즉시** 탈락 처리한다. 이 게임은 틱 기반이 아니라
  `word_cleared`/`word_missed` 이벤트가 발생하는 시점에만 HP가 바뀌는 이벤트 기반 판정 구조이므로,
  "다음 판정 사이클까지 대기" 같은 별도 유예 없이 해당 이벤트 처리 중에 즉시 탈락을 확정한다. 탈락한
  참가자는 이후 `word_spawn`을 계속 수신하되(관전 목적) 더 이상 `word_submit`을 판정 대상으로 취급
  하지 않는다. 탈락 시 서버는 `player_eliminated` 이벤트를 브로드캐스트한다(§WEBSOCKET_PROTOCOL.md
  §6.3).
- **매치 종료 — KO**: 탈락 처리 결과 생존자가 1명만 남으면 그 즉시 매치 종료, 마지막 생존자가 승리
  (`match_end.reason = 'KO'`).
- **매치 종료 — TIME_LIMIT**: 매치 상한 `180초`에 도달했는데 아직 생존자가 2명 이상이면, 그 시점의
  HP 내림차순으로 순위를 확정한다. 최고 HP가 여러 명이면 공동 1위(무승부)로 처리한다.
- **순위(rank)**: 탈락 순서의 역순으로 매긴다 — 마지막 생존자(또는 시간 초과 시 최고 HP 보유자)가
  1위, 그 직전에 탈락한 참가자가 2위, … 순. `match_end.ranking`에 실려 나간다.

### 3.2 단어 은행
- `src/game/acid-rain/word-bank.ts`에 정적 배열로 관리되는 **한국어 큐레이션 단어 300~500개**
  (현재 400개, `#73`).
- 각 단어는 `{ text, keystrokes }` 쌍으로 저장된다. `keystrokes`는 **음절 수가 아니라 2벌식
  키보드 기준 실제 타건 횟수**(`keystroke-count.ts`)다 — 쌍자음(ㄲㄸㅃㅆㅉ)·ㅒㅖ는 Shift 포함
  2타, 이중모음(ㅘㅙㅚㅝㅞㅟㅢ)·겹받침(ㄳㄵㄶㄺㄻㄼㄽㄾㄿㅀㅄ)은 두 키 조합 2타로 계산해서, 음절
  수가 같아도 실제 타이핑 시간이 다른 단어(예: "왜"(3타) vs "새"(2타))를 구분한다.
- `keystrokes`는 기본적으로 정적 하드코딩 값이다 — 계산 로직이 나중에 바뀌어도 이미 확정된
  단어들의 난이도가 조용히 변하지 않도록 하기 위함. 새 단어를 추가할 때는 `keystrokes: 0`으로
  두면 `countKeystrokes(text)`로 자동 계산돼 채워진다(값을 직접 계산할 필요 없음).
- **난이도 구간(버킷)**: 스폰 가중치·표시 등 상대적 난이도가 필요한 곳에서는 아래 구간을 쓴다.
  현재 단어 은행 분포 기준(400개)으로 각 구간이 고르게 나뉘도록 정함.

  | 구간 | keystrokes 범위 | 현재 단어 은행 내 개수 |
  |---|---|---|
  | LOW | 2~5 | 160개 |
  | MID | 6~9 | 184개 |
  | HIGH | 10 이상 | 56개 |

### 3.2b 낙하 위치·높이 동기화
두 클라이언트가 같은 단어를 "동일한 스트림"으로 인지하려면 가로 위치보다 **세로 낙하 진행도(높이)가
먼저 맞아야 한다**. 우선순위:

1. **높이(진행도) 동기화 — 우선순위 1.** 클라이언트는 단어 애니메이션 시작 시각을 로컬 수신 시각이
   아니라 서버 `word_spawn.spawnedAt`을 클록 오차 보정한 값으로 잡는다. 이렇게 하면 네트워크 지연이
   양쪽에서 달라도 같은 시각에 같은 높이로 보인다. 판정 자체는 서버 권위이므로 높이가 살짝 어긋나도
   결과에는 영향 없지만, 어긋난 채로 두면 "동일 스트림 브로드캐스트"라는 설계 원칙과 시각적으로
   맞지 않는다.
2. **가로 위치(레인) 동기화 — 우선순위 2.** 화면은 `LANE_COUNT = 5`개의 가로 레인(0~4)으로 나뉘고,
   서버가 스폰 시점에 레인을 배정해 `word_spawn.lane`으로 브로드캐스트한다. 현재 낙하 중인 단어들과
   겹치지 않는 레인을 우선 사용하고, 모든 레인이 사용 중이면 임의 레인에 배정한다. 판정은 텍스트
   기준이라 레인이 겹쳐도 게임 결과에는 영향 없는, 순수 시각적 일관성을 위한 보강.
3. 재접속 시 `state_sync`로 복구되는 진행 중 단어는 원래 배정된 레인과 낙하 진행도(spawnedAt 기준)를
   그대로 유지한다 — 새로 애니메이션을 시작하거나 위치를 재계산하지 않는다.

정본은 `WEBSOCKET_PROTOCOL.md` §6.3 "계약 확정 노트" 참고.

### 3.3 스폰 간격 (난이도 램프)
```
interval(ms) = max(700, 2000 - 50 * floor(elapsedSec / 10))
```
시작 2000ms에서 10초마다 50ms씩 빨라지며 700ms에서 바닥을 친다.

### 3.4 난이도 구간 가중치 (경과 시간별)
| 경과 시간 | 출제 구간 |
|---|---|
| 0~30초 | LOW만 |
| 30~90초 | LOW + MID |
| 90초~ | LOW/MID/HIGH = 40/35/25 가중치 |

각 구간 내에서 실제 단어는 균등 랜덤으로 뽑는다. (구간 정의는 §3.2 표 참고. `#75`에서
`WORD_BANK.filter(w => w.keystrokes <= 5)` 같은 방식으로 구간별 서브셋을 캐싱해 사용할 것을
권장 — 매 스폰마다 필터링하지 않도록.)

### 3.5 낙하 시간
```
fallDurationMs = (4000 + 250 * keystrokes) * max(0.6, 1 - elapsedSec / 300)
```
단어의 타건 횟수(`keystrokes`)에 비례해 기본 시간을 주되, 경과 시간이 늘수록 전체적으로
빨라진다. (예: keystrokes=2 → 시작 시 4500ms, keystrokes=17 → 시작 시 8250ms)

### 3.6 데미지
- **정타(단어를 먼저 지움)**: 지운 사람을 제외한 나머지 생존자 중 **서버가 무작위로 고른 1인**에게
  `5 + ceil(keystrokes / 2)` 데미지. 1:1에서는 유일한 상대가 대상이었으므로, N인에서도 "단일 대상"
  이라는 성격을 그대로 유지하기 위해 무작위 1인을 고른다(전원에게 주면 정타 하나의 파급력이 인원수에
  비례해 커져 게임이 지나치게 빨리 끝남). 지워진 단어는 전원 클라이언트에서 즉시 제거. (예:
  keystrokes=2 → 6, keystrokes=17 → 14)
- **미스(단어가 바닥에 닿음)**: **생존자 전원**에게 고정 `3` 데미지("산성비를 함께 맞는다" 컨셉 —
  1:1과 동일하게 유지, 인원이 늘어도 못 막은 실패는 모두가 공유). 탈락한 참가자는 대상에서 제외.

### 3.7 동시입력(레이스 컨디션) 처리
- 서버는 방마다 `word_submit`을 도착 순서대로 처리한다(Socket.io 룸 단위 단일 처리).
- 특정 `wordId`가 이미 `cleared` 상태면, 이후 도착하는 모든 제출은 `submit_rejected{reason:'ALREADY_CLEARED'}`.
- 같은 유저가 같은 단어를 재전송(네트워크 재시도 등)해도 서버가 멱등 처리하여 중복 판정하지 않는다.

### 3.8 재접속
- `disconnect` 시 **30초 유예**. 방은 유지되고 상대에게 `opponent_disconnected{graceMs:30000}` 알림.
- 유예 내 재접속: 클라이언트가 동일 `roomId`로 `join_room` 재전송 → 서버가 `state_sync`로 현재 HP,
  낙하 중인 단어 목록(남은 시간 포함), 경과 시간, 스폰 간격, **서버 현재 시각**을 스냅샷으로 전송.
- 유예 만료: 상대방 승리 처리(`match_end{reason:'FORFEIT'}`).

### 3.9 매치 종료 시 저장
- `MatchHistory` 엔티티에 저장. N인 배틀로얄에서는 참가자가 2~4명으로 가변이므로 `hostUser`/
  `guestUser` FK 2컬럼 고정 구조를 참가자 배열로 바꿔야 한다 — 실제 조인 테이블 마이그레이션은
  `#93`이 담당.
- `matchData` jsonb 목표 shape: `{ participants: [{ userId, finalHp, rank, wordsTyped }], durationSec }`.
  `rank`는 §3.1의 순위 규칙(탈락 역순, 마지막 생존자=1위)을 그대로 기록한다.

## 4. WebSocket 이벤트 스키마

전체 이벤트 정의(payload 상세)는 `WEBSOCKET_PROTOCOL.md` §6을 정본으로 한다. 이 문서는 게임 규칙만
다루고, 프로토콜 세부사항은 중복 기술하지 않는다.

## 5. 직업/클래스 시스템 없음

산성비 대전은 별도 직업이나 클래스 선택 없이 닉네임만으로 진행된다.

## 6. 향후 확장 여지 (과제 모듈 매핑)

- **AI 모듈(Major)**: AI가 사람 대신 단어를 입력하는 상대로 구현 가능 — 반응 지연에 랜덤성을 부여해
  "완벽하지 않은" 사람다운 플레이를 시뮬레이션. 1:1 전용으로 유지하며 아래 멀티플레이어 확장과는
  별개로 진행한다(`backend#99`).
- **Multiplayer game (3인 이상, Major)**: **진행 중** — `#91`(EPIC)/`#92`(본 문서, 규칙 확정 완료)
  기준으로 2~4인 배틀로얄 구현 착수. §1/§3.1/§3.6/§3.9 및 `WEBSOCKET_PROTOCOL.md` §0.1/§6.3 참고.
- **Tournament(Minor)**: 매치 자체가 짧고(최대 180초) 승패가 명확해 토너먼트 브래킷에 적합.
- **Game customization(Minor)**: 난이도 파라미터(스폰 간격, HP, 데미지 배율)를 방 생성 시 옵션화 가능.
